The HWM (High Watermark) authorization circuit's readiness rule, verified from `circuits/programs/authorization-btc-hwm/src/main.rs` (guest) + `circuits/crates/btc-segment-verifier/src/header_chain.rs` + `circuits/crates/circuit-types/src/authorization_btc_hwm.rs` on vault-provers branch `vk-upgrade-framework-hwm` (PR #395).

**Readiness rule (`verify_hwm_suffix_work`, §4 threshold):**
`suffix_work >= W_max * NOTICE_BLOCKS`, where:
- per-block work = `target_work_as_u256(target) = 2^256/(target+1)` (Bitcoin chainwork), accumulated as `U256`.
- `W_max` = max single-block work over the prefix **checkpoint..=tx_block** (inclusive; seeded with the checkpoint block's work).
- `suffix_work` = Σ work over blocks **strictly after** the gov tx's block, to tip.
- `NOTICE_BLOCKS` = build-time constant baked into the ELF (`include!(OUT_DIR/constants.rs)`, generated by build.rs from the chain-spec `[hwm] notice_blocks`; alongside `BTC_NETWORK`, `CHECKPOINT_*`). Per-network value; not yet re-verified exact integers (mainnet ≈ 7 days @10min).
- Threshold is **dynamic**, not a fixed per-network work value: it scales with observed hashrate (reversing the gov tx costs ≥ NOTICE_BLOCKS blocks of the strongest observed hashrate). Readiness is **monotonic** per upgrade (W_max & tx position fixed once included; suffix only grows).

NOTE: the threshold is NOT a `ChainParams` field (`ChainParams` has only pow_limit/target_timespan_secs/retarget_interval/no_retargeting/no_pow_check). It comes from `NOTICE_BLOCKS`.

**Witness (`AuthorizationBtcHwmInput`):** upgrade_kind, old/new vk_hash, prev_authority + next_authority (`AuthorityUtxo`), `header_chain: Vec<Header80>` = the **full post-checkpoint chain [h_cp+1 .. tip]**, `tx_block_offset`, `governance_tx: Vec<u8>`, `partial_merkle_tree` (BIP37). The circuit re-verifies the whole chain from the baked checkpoint (linkage/PoW/retarget/MTP), so the witness needs every post-checkpoint header, not just the suffix.

**Implication for btc-authz-db (PR #3) — confirms dropping the pushed `matured` list:** both readiness and witness are pure functions of stored state — (a) each upgrade's gov-tx block position, (b) post-checkpoint headers with per-block chainwork. So: (1) `apply_finalized_block` must NOT take a `matured` list (duplicates derivable state); monitor's per-block job = persist header(+work) + detected upgrades. (2) `ReadyToProve` is a **derived view**, not a stored transition (stored lifecycle = Pending→Proving→Proven). (3) the witness is **assembled on read** from stored headers + gov tx, not stored opaque at maturation. (4) the db must keep a **headers table** spanning checkpoint→tip; PR #3's collapse to a single `(height,hash)` cursor (commit 89182c4) is insufficient for both the readiness query and witness assembly. (5) the `cursor+1 == height` contiguity check is load-bearing — a gap breaks the linked chain the circuit requires and makes the work sums wrong (premature-ready = safety failure). See [[project_db_schema_in_pr]].
